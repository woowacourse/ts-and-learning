# 문제 3

## 막혔던 부분

Person은 Admin과 User둘다 가질 수 있어서 role을 확실히 가지는지 안가지는지 모름

그런데 person.role을 해버림

role을 가지고 있다는 확신을 어떻게 줘야하는지 모르겠음

## 해결을 위해 필요한 키워드 1개

타입 좁히기

## 키워드 단순 학습

타입 좁히기?

조건문 등을 이용해 넓은 타입에서 좁은 타입으로 타입을 상황에 따라 좁히는 방법

타입을 좁히는 방법

1. JS내장 타입일 때는 typeof로
2. 커스텀 타입일 때는 key in 변수로
3. 객체인지 확인하고 싶으면 변수 instanceof 객체

## 문제에 적용시켜 해결한 방법

“role” in Person으로 타입을 좁히게 되었음

## 키워드 심화학습 (생각해볼만한 질문)

Q1. **(Level 1 - 용어)** `typeof []`와 `typeof null`의 결과값은 각각 무엇일까요? (이 질문은 `typeof`만으로 타입을 좁힐 때 발생할 수 있는 위험성을 묻는 것입니다.)

A. 둘다 Object가 나오게 됩니다. 배열 또는 null을 정확히 검증할 수 없는 치명적인 오류가 존재합니다.

---

Q2. **(Level 2 - 설명)** `in` 연산자는 객체의 **속성 이름**이 있는지 검사합니다. 그런데 만약 `User`와 `Admin` 둘 다 `name`이라는 속성을 가지고 있다면, `if ("name" in person)`으로 타입을 좁히는 것이 가능할까요? 그 이유는 무엇인가요?

A. 타입 좁히기는 타입간의 차이점을 이용해 좁히는 방식을 사용하는 것 같은데, 공통 속성이 존재하는 상황에서는 타입을 구별할 수 없으니까 좁히기가 안될 것 같습니다.

---

Q3. **(Level 2 - 설명)** 현업에서는 `in` 연산자보다 **'구별된 유니온(Discriminated Union)'** 방식을 더 선호합니다. 두 인터페이스에 공통적으로 `type: 'user'` 또는 `type: 'admin'` 같은 속성을 추가하는 방식인데, 왜 `in`보다 이 방식이 유지보수에 유리할까요?

A. 나중에 user 또는 admin에 부가적인 속성이 추가되거나 삭제될 수 있는데, 만약 타입을 좁힐 때 사용되던 속성이 사라지면 유지보수 하기가 힘들어질 것 같아요.

---

Q4. **(Level 3 - 적용)** 다음 코드가 에러 없이 동작하도록 `isUser`라는 **'사용자 정의 타입 가드(User-defined Type Guard)'** 함수를 완성해 보세요.TypeScript

A.

```ts
function isUser(person: Person): person is User {
  if ("occupation" in person) return true;
  return false;
}
```

Q5. **(Level 4 - 변형)** 타입 좁히기를 완벽하게 수행해서 모든 경우의 수를 처리했다면, `else` 문에 들어오는 변수의 타입은 최종적으로 \**`never`*가 되어야 합니다. 왜 마지막에 `never` 타입이 할당되는 것이 코드의 안정성(예: 새로운 타입이 추가되었을 때의 대응)에 도움을 줄까요?

A. 모든 타입을 잘 좁혀놨기 때문에 그런거 아닐까요? 솔직히 잘 모르겠어요.

## 2회 이상 풀어보며 새로 깨달은 것

타입을 좁히는 방법은 위에서 언급한

```
1. JS내장 타입일 때는 typeof로
2. 커스텀 타입일 때는 key in 변수로
3. 객체인지 확인하고 싶으면 변수 instanceof 객체
```

3가지가 끝이 아니다

사용자 정의 타입 가드 등의 다양한 방식이 존재한다.
