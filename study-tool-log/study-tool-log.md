## **어떻게 도움이 되었는가**: 실제 사용 경험과 효과

1. 타입 가드를 꼭 써야 하는 이유 : person.type === 'user'로만 판단할 수 있는 거 아닌가?<br/>

   ```
   TypeScript의 타입 시스템은 조금 더 고지식합니다. 특정 함수(예: isUser)를 실행해서 true가 나왔더라도, 그 함수 밖으로 나오는 순간 컴퓨터는 다시 의심하기 시작합니다. "아까 그 함수가 true를 뱉긴 했는데... 그래서 지금 이 변수가 확실히 User 타입인 거야?"라고 묻는 것이죠.
   ```

   person is User라고 명시하지 않으면 함수를 통과해도 타입은 여전히 `User | Admin` 합집합 형태로 남아 있는다.

   -> 타입 가드를 명시적으로 작성해야 컴파일 단계에서 안전성이 보장된다는 것을 알게 되었다. 이를 통해 런타임이 아닌 컴파일 단계에서 오류를 사전에 방지할 수 있게 되었다.

2. personType: "user"라고 직접 적어도 되지 않을까? <br/>

   ```
   TypeScript는 이를 방지하기 위해 "데이터의 원천(Source of Truth)"을 하나로 고정하고 싶어 합니다. personType을 "user"라고 직접 적는 것은 값을 복사해서 붙여넣는 것과 같습니다. 나중에 User 인터페이스의 type이 "member"로 바뀌면, 리터럴로 적은 모든 곳을 찾아다니며 고쳐야 하는 불상사가 생깁니다.
   ```

   User['type']은 User 타입에 종속되어 있어 User 타입이 변하면 같이 변한다. 따라서 일일히 찾으면서 수정할 필요가 없다.

   -> 문자열 리터럴을 직접 사용하는 방식이 아닌, User['type']과 같이 타입에 종속된 형태로 작성해야 유지보수가 쉬워진다는 것을 이해하였다.

3. swap 메서드에서 반환값을 지정해줘야 되는 이유가 뭘까 <br/>

   ```
   만약 반환 타입을 지정하지 않으면, TypeScript는 [v2, v1]을 보고 "아, 이건 그냥 T와 U가 섞여 있는 일반적인 배열((T | U)[])이구나"라고 뭉뚱그려 생각합니다. 그러면 나중에 첫 번째 요소가 U 타입이라는 것을 보장받지 못하게 됩니다.
   ```

   튜플 타입을 사용하여 데이터의 위치가 바뀐 것을 정확하게 알려준다.

   -> TypeScript의 타입 추론이 항상 개발자의 의도를 완벽하게 반영하지 않는다는 것을 알게 되었고, 특히 swap과 같은 경우 반환 타입을 명시하지 않으면 정확한 타입 정보가 손실된다는 점을 이해하였다.

4. Omit과 교차 타입의 결합 순서에 대해 질문

```
type PowerUser = Omit<User, 'type'> & Omit<Admin, 'type'> & { type: 'powerUser' };

type PowerUser =Omit<User & Admin, 'type'> & { type: 'powerUser' };
```

위의 코드에서 Omit으로 속성을 제거한 후 & 연산자를 사용하여도 되지 않을까?

```
JavaScript에서는 Object.assign()이나 스프레드 연산자(...)를 써서 여러 객체를 합칩니다. 이때 속성이 겹치면 뒤에 오는 것이 앞의 것을 덮어씌우죠. 하지만 TypeScript의 & 연산자는 단순히 "덮어쓰기"가 아니라 "두 타입의 조건을 모두 만족해야 함"을 의미합니다. 만약 두 타입이 같은 이름의 속성을 가졌는데 타입이 서로 다르다면, 그 속성은 불가능한 타입인 never가 되어버립니다.
```

&는 A이기도 하고 동시에 B이기도 해야 한다는 뜻이다. 예를 들어 id가 한쪽은 string, 다른 쪽은 number인 경우, 두 가지를 동시에 만족하는 값은 존재하지 않기 때문에 never 타입이 되어버린다.

-> TypeScript의 & 연산자가 단순한 객체 병합이 아니라 모든 조건을 동시에 만족해야 하는 타입이라는 점을 이해하면서, 타입을 설계할 때도 논리적으로 사고하게 되었다.
