**[현재 부족한 핵심 역량]**

1. 비동기 패러다임의 전환 능력: 실행 순서를 보장하기 위해 함수를 중첩시키던 '콜백' 방식을, new Promise를 사용하여 상태(Pending, Fulfilled, Rejected) 중심의 객체로 감싸는(Wrapping) 로직이 익숙하지 않은 상태입니다.

2. 제네릭(Generics)의 실전 활용: 단순히 타입을 지정하는 것을 넘어, 함수가 호출될 때 들어오는 데이터 타입을 추론하여(T) 반환 타입까지 연결하는 '타입 변수' 활용 능력이 요구됩니다.

3. 고차 함수(Higher-order Functions) 이해: 함수를 인자로 받거나 새로운 함수를 반환하는 구조에 대한 이해가 필요합니다. promisify는 함수를 입력받아 새로운 비동기 함수를 뱉어내는 전형적인 고차 함수입니다.

```
## 딱 하나의 개선안 — **"직접성(Directness)" 원칙의 적용**

당신의 학습 흐름을 보면 현재 이런 구조입니다.
```

문제를 만남 → 진단 → 로드맵 → 개념 학습 → 문제로 돌아옴

```

이 구조의 문제는 **개념 학습과 실전 사용 사이의 거리**입니다. Promise를 따로 공부하고, Generics를 따로 공부한 뒤 문제로 돌아오는 방식은 전이(transfer)가 잘 일어나지 않습니다. 배운 것을 실제 문제에 연결하는 작업이 또 하나의 장벽이 됩니다.

제가 제안하는 단 하나의 개선은 다음입니다.

### 🎯 "문제 안에서" 개념을 학습하는 구조로 전환하기
```

문제를 만남 → 진단(AI) → [문제를 붙잡은 채로] 개념 학습 → 즉시 적용
구체적으로는 이렇습니다. 10번 문제에서 promisify 구현이 막혔다면, Promise 개념을 별도 문서나 강의로 공부하는 것이 아니라, 10번 문제의 코드를 열어놓은 상태에서 필요한 만큼만 찾아보고 즉시 적용하는 것입니다.
javascript// ❌ 분리된 학습 (전이 비용 발생)
// 1단계: Promise 튜토리얼 정독
// 2단계: Generics 예제 연습
// 3단계: 다시 10번 문제로...

// ✅ 직접적 학습 (전이 비용 최소화)
// 10번 문제를 열어놓고 →
// "왜 여기서 new Promise가 필요한가?" 만 찾아보고 →
// 바로 이 코드에 적용해보기
function promisify<T>(fn: Function) {
return function(...args: any[]): Promise<T> {
return new Promise((resolve, reject) => {
// 여기서 막히면 → 이 줄만 찾아보기
fn(...args, (err: Error, result: T) => {
if (err) reject(err);
else resolve(result);
});
});
};
}
이 방식이 효과적인 이유는 학습한 개념이 즉시 맥락(context)과 함께 저장되기 때문입니다. "Promise는 상태를 갖는 객체다"라는 추상적 지식이 아니라, "promisify에서 콜백 결과를 감쌀 때 new Promise가 필요하다"는 맥락 있는 지식으로 저장됩니다.
