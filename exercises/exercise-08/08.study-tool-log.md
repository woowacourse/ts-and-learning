문제 번호: [ #08 ]

1. 이 문제가 학습하길 의도하는 개념(내 추측)
[ Omit, &(intersection) ]
- Omit: 존재하는 타입을 재활용해 화정 property만 빼고 재정의하는 Omit 을 익히는 것
- &: 여러 타입을 결합하는 것 

2. 풀이 접근
[ &(intersection) ]
- Omit<(User & Admin), 'type'> & { type: 'powerUser' };
  - 이건 왜 안되나?
  - 나는 처음에 User와 Admin 이 interface로 정의되어 있어서 인가 했는데 그런 차원의 이야기는 아님
    - Q. interface로 정의하건 type으로 정의하건 상관없나?
      - |, &, extends 연산자 사용시 피연산자의 타입 선언 방식에 따른 제약이 있나?
    - A. 타입을 조합하는 연산(타입 연산)산 타입을 선언하는 방식(타입 선언 방식) 사이의 의존은 없다
      - 타입 연산자(|, &, extends)는 피연산자의 선언 방식(type vs interface)과 무관하다
      - 피연산자 제약은 피연산자 선언 방식이 아니라 타입의 종류에 의해 결정된다
    - 타입 레벨 연산
      - 컴파일 타입에 계산됨
  - & 로 정의시 같은 key가 충돌될때 어떻게 되는지 이해가 부족 했던 것
    - intersection(교차 타입) 에서 같은 키 충돌이 남
      ```
        {
          type: 'user' & 'admin'; // ❗ 여기서 문제 발생
        }
      ```
  - never
    - 교차타입은 잘못 사용하기 쉽고 불가능한 타입을 생성함
    - 원시타입의 값은 동시에 여러 타입이 될수 없기 때문에 교차 타입의 구성 요소로 결합할수 없음
    - 두개의 원시타입을 함께 시도하면 never 키워드로 표시되는 never 타입이 된다

    - never 키워드, never 타입은 프로그래밍 언어에서 bottom 타입과 empty 타입을 뜻함
      - bottom: 값을 가질수 없고 참조할수 없는 타입이므로 botttom 타입에 그 어떤 타입도 제공할 수 없다

    - 이미 type: never 인 상태에서 제거됨 
      - 이라고 함
      - 중간에 이미 깨진 타입을 만들어 버린 것

3. 실제 문제 의도 (ai)
[ type composition, utility type 순서제어 ]
- type composition
  - 기존 타입을 제사용한다
  - & 교차타입의 동작을 이해한다
  - Omit을 언제 적용해야하는지 안다
- utility type 순서제어
  - 교차(&) 전에 충돌을 제거해야 한다
  - 1. User & Admin 먼저 수행됨
  - 2. type: 'user' & 'admin' → never -> 깨진 타입이 생성 됨

4. 틀린 이유 (정리)
[ intersection, never ]

[[내 접근]]
- User와 Admin을 먼저 합친 뒤, 충돌나는 type을 제거하고 다시 정의하면 된다고 생각힘

[[그럴듯 했던 이유]]
- & 를 객체를 합치는 느낌으로 이해함
- 두타입을 합치면 모든 속성을 가진 타입이 된다고 생각

[[핵심 착각]]
- intersection 를 객체 병합처럼 생각함

[[실패 원리]]
- 같은 key가 있을 경우: 
- ```type: 'user' & 'admin'``` 처럼 계산되면
- never로 처리됨

[[정정된 규칙]]
- A & B는 병합이 아니라 동시 만족이다
- 같은 key가 충돌시 양립이 불가능하면 never가 된다

[[적용 기준]]
- & 를 사용할때 같은 key가 양쪽에 존재하면 반드시 확인한다

[[관련된 개념 정리]]
- intersection Type &
	-	두 타입을 모두 만족하는 타입을 생성
