1. 이 문제가 학습하길 의도하는 개념(내 추측)
[ optional/union, sub typing ]
- optional/union 
  - 둘중 하나로 풀어도 테스트 통과에는 상관이 없음
  - 타입 테스트 코드에서 보는 건 타입의 구조만 봄
  - Person 을 새로 정의해서 age 와 occupation 을 optional로 두는게 좋을지 
  - User 와 Admin 을 union 으로 연결 시킬지
  - 이미 User, Admin 이 있고 이미 있는 시스템이 돌아가고 있다는 전제니까 새로 타입을 처음부터 만들지 않고 union 을 이용해서 타입을 새로 만든다
- sub typing
  - 함수 매개변수의 타입 정의
  - 서브 타이핑 관점
  - 좁은 타입 -> 넓은 타입으로 전달 가능

2. 풀이 접근
[ union, sub typing ]
- union
  - union 으로 합치면 공통되는 속성만 접근 가능함
  - A | B = A와 B의 교집합만 안전하게 사용 가능
- sub typing
  - 구조적 타입 시스템
    - 타입이름을 이름이 아니라 구조로 판단
  - 서브 타이핑
    - 더 많은 프로퍼티를 가진 타입은 더 적은 프로퍼티를 요구하는 타입의 서브타입
    - 좁은 타입 -> 넓은 타입으로 전달 가능
    - argument -> parameter

    ```
      type B = string | number;
      function funcB(b: B){} // parameter
      const b = 'string'; // argument
      funcB(b);
    ```

    ```
      { age: number } // 넓은 타입
      { age: number; name: string } // 좁은 타입, 서브타입
    ```

  - 서로 다른 구조를 하나의 배열에서 다루기
  - 이때 필요한 개념이 Union 타입, 공통 인터페이스 관점이라고 이라고 함

4. 틀린 이유
[ union ]
  - 테스트 통과는 되었지만 union 자체에 대해서 잘 이해를 못했다
  - union 으로 처리하는 것과 optional 로 처리하는 것은 다름
  - optional 의 경우 둘다 있을수도 있음(User도 아니고 Admin도 아님)
    ```
      type Person = {
      name: string;
      age: number;
      occupation?: string;
      role?: string;
    }
    ```
